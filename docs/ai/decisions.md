Newest first. One entry per non-obvious decision: what, why, what was rejected.

## 2026-11-13: The launcher: overlay, Ctrl+P and scoped search of tabs and commands (M2.1)
- **The plan is `planning/m2-plan.md`** (decisions L1 to L7). M2 is split in three: M2.1 (this), M2.2 history and bookmarks with `Ctrl+D`, M2.3 Home Screen entries and ranking.
- **A second trusted view, not part of the sidebar.** The launcher is `app://shell/launcher.html` (a second Vite entry of the same UI), created before the window and added with `add_overlay_view` (custom docking), hidden until `Ctrl+P`. It has its own client role (`Role::Launcher`): as trusted as the shell (IPC accepted only from an `app://shell/` frame of that view), but its own key rules (only `Esc` and `Ctrl+P`, both close it; every other key is for its search box, so no window-level shortcut fires while it is open) and its own replies (anything named `launcher.*` goes to the launcher view only, never to the sidebar). No request context, like the shell.
- **Scope is held and enforced in core** (`backend/launcher.rs`). The page sends `launcher.scope {kind: contextual | selected | all, workspaces}` as a **request**; core resolves it to existing workspaces (unknown or malformed ids are dropped; a selection with nothing valid falls back to the **active workspace, never to a wider scope**) and keeps the result. A search carries **only the query** (the message refuses any other field), and **only the databases of workspaces in scope are opened**, so out-of-scope data is never read, not read and then filtered. Closing the launcher (or running a result) resets the scope in core (S4).
- **Results are opaque ids**: `tab/<workspace>/<tab>` and `cmd/<id>`. `launcher.run` checks a tab result against the scope *as it is at that moment* (S2): a tab of a workspace outside it is refused with a message that names nothing from that workspace. Empty query shows the scope's open tabs and then commands. **No result list, recent list or suggestion cache is kept anywhere** (S3); every search is computed afresh. A query is capped at 256 characters and a reply at 30 results.
- **Fuzzy search** (`search.rs`, pure text): every word of the query must match as a subsequence, case ignored; a contiguous match beats a scattered one, a match at the start of the text or of a word beats one inside it, shorter text breaks ties; open tabs rank slightly above commands with the same match. A tab matches on its title (double weight) or its address. Tested with odd and non-ASCII text.
- **Commands from the launcher.** Every registry command is a result (by label or id) except the launcher itself; running one closes the launcher first, then runs the command, so a command that moves focus (`New workspace`) is not undone by the launcher handing the focus back to the page.
- **Dragging.** The title bar sends `launcher.drag {dx, dy}` (movement only, clamped to 4000 in core); the host clamps the overlay inside the window (also when the window is resized) and saves the position in the global settings when the launcher closes. It starts top-centre. The page uses mouse events on `window` while dragging, because jsdom (the tests) has no pointer events; a real drag was checked on the real window.
- **After closing, the page gets the focus back** (L7). Restoring a previously focused address bar is not done: the sidebar has no notion of "previous control", and the page is where you were going.
- **S1, S2, S3, S4**: tests in `backend.rs` (a Work-scoped search never contains Personal data, also not in errors or the open reply; the client's scope is a request; a result from a wider scope cannot be run once narrowed; no result list is kept; closing resets). **S1 is complete for tabs and commands only**: history and bookmarks come in M2.2, and the S1 row stays open until they do.
- **Checked on the real window** (`tools\m21-launcher.ps1`): `Ctrl+P` from a page input, a frame of a page and the address bar; `Esc` and a second `Ctrl+P` close it and the page has the keys back; a real mouse drag moves it and it reopens where it was left; a page title that exists only in another workspace is not found by a normal search, is found and opened after "All workspaces" is chosen, and is not found again the next time the launcher opens; "New tab" run from the launcher makes a tab.
- **Not done in M2.1:** history, bookmarks and Home Screen entries (M2.2, M2.3), ranking by recency and frequency, scope rules for split view (M4), remembering a focused address bar, a launcher that grows with its results, IME (not checked), and the launcher's own accessibility review beyond roles and labels.
- **Tooling:** `Drag-Client` in `tools\lib\app.ps1` (a real, stepped mouse drag); a test page whose title only the launcher search should find.

## 2026-11-13: Restore, window state, the soak and the exit test (M1.7)
- **What was already restored:** workspaces, tabs, groups, the selected tab and each workspace's login (the profile folder) live in databases and profile folders written as things change, so a clean close and a **kill** both bring them back; the M1.3 and M1.2 checks covered the clean case, `toolsm17-restore.ps1` now covers the kill.
- **Window state (`settings::WindowState`).** Size and maximised state are saved at close and restored at start. **Size only, never a position**: a window restored onto a monitor that is gone would be unreachable. The stored text is parsed defensively and clamped (480x320 to 16000x16000; junk means the default). A maximised window keeps the size it had before, so un-maximising gives a sensible window. Saved on a clean close only; after a kill the previous size is used.
- **Killed app (checked on the real window).** Two workspaces, four tabs and a login in each workspace: after a kill the same tab was selected, both tabs of the second workspace were back, and each workspace still had its **own** token (cookie and localStorage) from before the kill, not the other's. **Bound:** a login made in the last ~30 seconds before a kill can be lost, because Chromium flushes cookies on that interval; the script waits 40 seconds first. Not worked around.
- **Soak (`toolssoak.ps1`).** 14 tabs over two workspaces, a tab visited and a page loaded every 6 seconds, a tab closed and reopened every 5 steps, a workspace switch every 17, for 12 minutes: **14 processes throughout, 843 MB (second quarter) to 846 MB (last quarter), +0.4%**. The bound the script enforces: at most 22 processes and at most 40% growth between the second and last quarters. A multi-hour run is the same script with `-Minutes 240`; it has not been run.
- **Exit test on real accounts** is a hand procedure (`planning/m1-exit-test.md`) because it needs your real logins. **Not run yet.**
- **Not done, deliberately:** the `0.2.0-alpha` tag and a release page (you said to keep it unreleased until you say), the hours-long soak, and the hand exit test; these three are the remaining gate for M1.

## 2026-11-13: Safety nets: error pages, certificate errors, popups, notices and downloads (M1.6)
- **Own error pages (`core::errorpage`).** A failed main-frame load, a certificate error and a crashed page each get a page the app generates: no script, a CSP of `default-src 'none'`, every outside string (the address, CEF's error text) HTML-escaped and cut short, loaded as a `data:` address. The tab keeps the address that failed (the address bar shows it, and a `data:` address is never stored as a tab's address); **Reload retries the failed address**, not the error page. A load cancelled by a new navigation or Stop (`ERR_ABORTED`) shows nothing. Tests: hostile text, no way past on the certificate page, the data address has only safe characters.
- **S12: certificate errors are never bypassed.** `on_certificate_error` returns 0 (cancel) explicitly and logs; the load error that follows shows the certificate page, which has no link or button past it. Checked on the real window against a local https server with a self-signed certificate (`tools\m16-safety.ps1`): the page is shown and **no request reaches the server, even after a reload**. **The check has teeth:** with the handler changed to continue the request it fails on all three assertions (the server saw 5 requests). Not built: a per-site "trust this certificate" memory, deliberately; if it ever exists it needs its own decision.
- **A crashed page and a crashed shell.** `on_render_process_terminated`: a page gets the crash page (its tab and every other tab are unaffected); the shell is reloaded, at most 3 times per run so a shell that dies at once cannot loop. Checked by killing every `--type=renderer` process of the running app: crash page shown, shell back, browsing works.
- **Popup policy (`Backend::popup`).** The native popup window is never made (`on_before_popup` returns 1). The request goes to core on a UI task: a popup **the user asked for** (CEF's user-gesture flag), to an http(s) address, from a page of the **active workspace**, becomes a new tab of the same workspace (its profile, S10 again); anything else is blocked with a notice; a background workspace's page gets nothing, not even a notice. **FINDING:** Chromium's own popup blocker stops a script-opened popup without a gesture before the app is asked, so the app's refusal is the second layer; both are fine and the check only asserts that no tab appears.
- **Notices (`Backend::notice`).** A dismissed JavaScript dialog, a denied permission or camera request, and a blocked popup show a short plain-text notice in the sidebar footer (at most 5 kept, dismissable). The text is made in the host from the page's origin, flattened and capped in core, shown as text (never markup; tested), and **only for a page of the active workspace**, so a background workspace cannot talk to the shell (S11). The real prompts and the media decision store stay M4. JavaScript dialogs and permission prompts are still answered by the app (cancel, deny): the M0 finding that CEF's own dialogs crash the app when their view is destroyed still stands, and this is what "app-owned" means until M4.
- **Downloads, minimal.** **FINDING:** CEF's `DownloadHandler::can_download` defaults to 0, so with no override no download ever starts and `on_before_download` is never called; it now allows a page (not the shell). A download is **held** (the callback is kept in the host, nothing is written) and offered in the sidebar (Save or Cancel, or `Ctrl+Shift+S` / `Ctrl+Shift+X` for the oldest waiting one: keyboard-first). The shell sends only `download.decide {id, save}` for an offer core made (unknown or already answered ids are an error; extra fields are refused, so no path can be smuggled in). **The folder is the app's** (the user's Downloads folder; `--downloads-dir` in tests) and the **name is made safe in core** (`downloads::safe_name`: last path component only, no reserved Windows names, no control or special characters, at most 100 characters, never empty) and **never overwrites** (`report (2).txt`). At most 4 offers wait; a download from a background workspace is cancelled at once; closing the tab cancels its waiting downloads. Cancel is dropping CEF's callback without calling it. **Rejected:** a folder picker (the spec's "chosen folder" is a later setting; the shell must not be able to name a path), and a download shelf with progress (M4 or later).
- **The M0 destroy-on-busy-page and permission checks now run against the production code** (`tools\m16-safety.ps1`, section 1): an alert, a confirm, a prompt, a geolocation request, a notification request, a camera request, a `beforeunload` page and a page in an endless loop are each closed while active; each view is destroyed, the window keeps responding and the process count does not grow (7 before, 8 after the whole run).
- **Not done in M1.6:** the media decision store and the capture-stop wrapper (designed in the plan, built in M4); real permission and dialog prompts (M4); download progress and a folder setting; permission labels by kind (the notice says "a permission"); a "page unresponsive" message for a hung renderer (the busy page can be closed, which is what the check needs).

## 2026-11-13: Navigation chrome, search-or-address entry, favicons and opening across workspaces (M1.5)
- **Where it lives: the top of the sidebar, not a toolbar over the page.** Back, forward, reload or stop, and the address bar sit above the workspace tree. This follows the vertical-tabs design (the spec's left sidebar) and avoids a second trusted view and a nested window layout; the cost is a 220 px wide address field, which scrolls and selects all on focus. A wider, resizable sidebar is a later change. **Rejected:** a toolbar view above the pages (extra layout nesting and a second shell view for little gain now).
- **What was typed is decided in core (`address::resolve`), never in the shell or the host.** Rules, in order: `http://` or `https://` as typed; `about:blank`; text with no spaces that starts `scheme:` and is not a host and port is a scheme the app does not open and is **refused with a message** (`javascript:`, `data:`, `file:`, `app:`, `chrome:`, `view-source:`, `mailto:`, `ms-settings:` and so on), never searched or loaded; text that looks like a host becomes an address (`http://` for `localhost`, `*.localhost` and IP literals including `[::1]`, `https://` for names); anything else is a **search** (DuckDuckGo, percent-encoded, up to 2 KiB). `user@host`, `3.14` and single words are searches, not guesses. Whatever is typed, the result passes `url::is_restorable` (tested with hostile inputs). The shell sends `nav.go {input}`; core answers with a `Navigate` effect for the **selected tab only** (the message has no tab field), and the host checks the address once more before loading it.
- **Navigation commands** (all in the registry, all with shortcuts, all unit-tested): `Alt+Left` back, `Alt+Right` forward, `F5` or `Ctrl+R` reload, `Ctrl+Shift+R` reload ignoring the cache, `Ctrl+.` stop, `Ctrl+L` go to the address bar. Arrow keys and `.` became chord keys; a bare arrow key still belongs to the page. The shell's buttons run the same commands.
- **Loading state, title, address and back/forward per tab.** The host keeps this for every tab with a view and pushes a `nav` message (core cleans the address and title: control characters removed, length capped) for the shown tab only. The address field does not overwrite what you are typing; it shows the blank page as empty.
- **Favicons are fetched in the tab's own context and gated by core.** CEF announces the page's icon addresses; the host downloads the first http(s) one **through that tab's own browser** (so its workspace's request context), re-encodes it as a PNG (CEF's encoding of the decoded image, not the page's file), and hands the `data:image/png;base64,` address to core. Core keeps it for the session only (never stored), accepts only that exact form up to 32 KiB for a tab that exists in that workspace, and **includes it in the `tabs` reply only for expanded workspaces**, so a collapsed workspace's icons never reach the shell either (S11 extended; tested). The shell accepts only a PNG data address as a tab icon. **FINDING:** CEF's `Image::as_png` returns nothing when the size out-parameters are `None`; and a `CefStringList` lent to a callback cannot be cloned (the copy is empty): it has to be read through its raw pointer.
- **S10: opening across workspaces uses the destination's profile.** `tabs.open_in {workspace, url}` (the sidebar's "-> <workspace>" buttons, shown for the current page) creates a new tab **in the destination workspace's own database**, switches there, and the `Show` effect names the destination, so the host builds the view in the destination's request context. The address must be restorable (web addresses only). Checked on the real window with a page that stores a token in a cookie and localStorage: opened from workspace one in workspace two it saw none of workspace one's (workspace two made its own); opened from workspace two in workspace one it saw workspace one's own token and not workspace two's. **The check has teeth:** with the host changed to build a new view in another workspace's profile it fails on three assertions (workspace two saw workspace one's token).
- **Checked on the real window (`tools\m15-navigation.ps1`):** typing an address (an IP and port got http://), the page icon, a real link click, Back, Forward, Reload, a search (DuckDuckGo loaded), `javascript:` refused, Stop cancelling a slow load (with a control that the same load finishes when left alone), browsing in a second workspace, and S10 in both directions.
- **Tooling:** `Send-Text` can type common punctuation (US keyboard layout assumed); the test server serves PNGs and delays a response with `?delay=<ms>`; test pages for navigation (`nav-a`, `nav-b`, `slow`, `icon.png`). A UI bug found by the new tests: the "open in" row read `nav.url` on the signal instead of `nav.value.url` and would never have appeared (TypeScript is not type-checked in this project).
- **Not done in M1.5:** certificate and error pages and load-failure pages (M1.6), the stronger focus cue, address suggestions and history (M2 and later), a progress percentage (loading is a bar, not a number), opening a link in another workspace from the page's own context menu, and a configurable search engine.

## 2026-11-13: The sidebar tree, groups and the accent frame (M1.4)
- **A collapsed workspace is only a name and an icon, and the data is never sent (S11).** Core keeps the set of expanded workspaces (session state: the active one at start) and the `tabs` reply carries a **section per expanded workspace only**: its groups, its tabs in visual order and its selected tab. A collapsed workspace has no section, so its titles and addresses never reach the shell at all; the shell cannot show what it was never given. The collapsed row is built from the workspace record alone (chevron, icon letter on the workspace colour, name; no tooltip, count or badge). Tests at both ends: `a_collapsed_workspaces_tabs_never_appear_in_the_reply` in core, and the S11 suite in `ui/src/Sidebar.test.tsx`, which renders the real sidebar in jsdom with titles and addresses that must not appear anywhere in the HTML, text or attributes (shown to fail when a tooltip and a count badge are added). **Behaviour as agreed in the spec:** the name activates the workspace (restoring its last tab); the chevron expands or collapses without switching (`workspaces.expand`); clicking a tab of another expanded workspace switches to it and collapses the others (`tabs.open`, which checks the tab is in that workspace's own database); activating any workspace expands it and collapses the rest. Only the active workspace's tabs have close buttons; other workspaces' tabs can only be opened.
- **Groups.** `tab_groups` (already in the schema) are now used: `group.rs` creates a group around a tab, renames, collapses (persisted) and assigns tabs; a group with no tabs is deleted. **One visual order:** `tab.position` is the order the sidebar shows and `Ctrl+Tab` walks: ungrouped tabs first, then each group in group order with its tabs together. `tab::normalize` restores that after every change, so a move cannot take a tab out of its block, and a new tab opened from a grouped tab joins its group. Messages: `groups.new|rename|collapse`, `tabs.group` (a missing `group` field is refused: serde would otherwise read it as null, "ungroup"). Commands: `Ctrl+Shift+G` (group the tab), `Ctrl+Shift+U` (ungroup), and `Alt+N` (new workspace: opens the name field in the sidebar, so a workspace can be made by keyboard). In the sidebar `Right` and `Left` expand and collapse the focused workspace or group, and `F2` renames a group.
- **The accent frame.** Every page sits in its wrapper panel with a 3 px inset, and the wrapper's background is the workspace colour (core sends it with each `Show` and a `SetAccent` when the workspace is recoloured, which repaints the open pages at once). **FINDING:** setting the wrapper's background colour only when the wrapper is created paints nothing; it must be applied again once the wrapper is in the window (M0's outline code did this on every focus change, which is why it worked there). The frame is a visual cue, not a security boundary (spec). Checked on real screenshots: blue for the first workspace, the next palette colour for a new one, the frame follows the switch, and changes live on recolour.
- **S8, no flash.** `tools\s8-switch.ps1` makes three workspaces show three colours on the same address (each is its own profile, so each keeps its own colour in localStorage), records the window at 60 fps while cycling `Alt+PageDown`, and checks with `analyze-frames.js --cycle` that the frames go round green, red, blue in order: each change moves to the *next* state and a frame of the previous workspace never comes back; only a dark gap may sit between. Result: 9 switches over 900 frames, 10 states, no out-of-order frame and no gap frames at all; a second recording of tab creation and closing showed only the page colour and gaps of one or two frames (about 17 to 33 ms) of dark. The check **has teeth**: with the host changed to never hide the previous view it fails ("only 1 state seen"). A `--min-states` requirement was added for exactly that case; without it a check that only forbids wrong transitions would pass on a switch that does nothing.
- **Tooling lesson: the desktop steals focus.** One run failed because something else took the foreground mid-run, so later keys went elsewhere. `Send-Keys` and `Click-Client` now bring the app window back first and count it; the long scripts print a note when that happened, so a run reports it rather than failing mysteriously.
- **Not done in M1.4:** drag and drop reordering (moves are by shortcut), per-group colours, persisting which workspaces are expanded across restarts (expansion is session state by design), closing tabs of an expanded inactive workspace without switching to it, and the stronger frame for the focused pane (split view, M4). Not asked and not added: icons other than the workspace's initial letter.

## 2026-11-13: Tabs, the command registry and window-level shortcuts (M1.3)
- **Tabs are records; views are disposable.** A tab is a row in its workspace's own database (id, address, title, position; the selected tab is in `workspace_state`). Its page view exists only while needed. Core decides which views are alive (the 8 most recently shown, `MAX_LIVE_VIEWS`) and returns effects (`Show`, `DestroyView`, `DeleteWorkspace`, `FocusPage`, `FocusShell`); the host only carries them out and creates a view from the record when a tab is shown. Closing the visible tab shows its neighbour first and only then destroys the old view (never a blank window); closing the last tab opens a fresh one; a workspace always has a tab. A tab id from another workspace is "no such tab" for every operation.
- **Addresses and titles are untrusted.** A tab address is only stored, and only ever loaded again, if `url::is_restorable` allows it: `http`, `https` and `about:blank`, no whitespace or control characters, at most 8 KiB. So `javascript:`, `data:`, `file:`, `blob:`, `chrome:` and the app's own `app:` can never be restored, and a start address of `app://shell` becomes the blank page. Titles are cleaned (control characters, 200 characters) before storing.
- **One command registry (keyboard-first).** `core::commands` lists every command with its default chords; the shell's buttons, the shortcut handler and (M2) the launcher all run a command by id through `Backend::run_command`. The host matches chords in the pre-key-event handler of **every** view, so no shortcut depends on which view has focus (checked with focus in a page, in an iframe and in the sidebar), and a matched chord is swallowed: a page never sees it (checked: a page that logs every key saw none). Chords: `Ctrl+T`, `Ctrl+W`, `Ctrl+Tab`, `Ctrl+Shift+Tab`, `Alt+1`..`Alt+9`, `Ctrl+Shift+PageUp/PageDown` (move), `Ctrl+Shift+D` (unload background tabs), `Alt+PageUp/PageDown` (workspace), `F6` (sidebar and page), `Esc` (in the sidebar only: back to the page). **Rules:** no chord uses Ctrl and Alt together, because Windows reports AltGr as Ctrl+Alt and such a chord would swallow typed characters (an earlier `Ctrl+Alt+D` was dropped for this); `Ctrl+1`/`Ctrl+2` (split-view pane focus, M4), `Ctrl+P`, `Ctrl+D`, `Ctrl+\` and `Ctrl+Shift+P` stay free for the spec's later features; `Esc` is shell-only so pages keep it. Tests fail on any duplicate chord, on a Ctrl+Alt chord, on a promised chord being taken, and if `docs/.../reference/shortcuts.md` does not list every chord.
- **FINDING 1, leaked browsers (fixed).** The first version detached each tab's `BrowserView` from the window and called `close_browser`. `on_before_close` never fired and every closed tab left a renderer process behind (8 cycles: 13 to 29 processes, 655 MB to 1.4 GB). `try_close_browser`, a non-forced close, hiding first and holding the view all failed to help; closing before detaching takes the whole app down (as in M0). **What works, and what M0 had always done without my noticing:** every tab's view lives inside a **wrapper panel**, and it is the wrapper that is shown, hidden and detached; a browser view with no parent at all never finishes closing. After the change 200 open / go back / unload / recreate / close cycles went from 7 processes to 7 (peak 8), memory 360 MB to 392 MB, 407 views created and 406 destroyed. This also explains the M1.2 data-removal finding (see the correction there). The wrapper is also where M1.4 draws the workspace colour frame.
- **FINDING 2, a resource request handler cancels by default.** Adding a `ResourceRequestHandler` (to refuse external protocols) made every request of every page fail: the trait's default `on_before_resource_load` answer is 0, which is CANCEL. It now returns CONTINUE explicitly. The handler denies every operating-system launch of a non-web protocol (`mailto:`, `ms-settings:`, ...) and logs it; the real prompt UI is M1.6.
- **FINDING 3, links to the app scheme do nothing.** `app://` is registered display-isolated, so a real click on a page's link to `app://shell` starts no navigation at all (no load, no error, nothing handed to the operating system). The S6 check now clicks such a link and, as a positive control, an ordinary link that must be followed.
- **FINDING 4, `window.close()` is not honoured** for a tab that script did not open: nothing closes. The path "a page closed its own view" (`Backend::view_closed_by_page`, which shows a neighbour) is covered by unit tests only; it will matter for popups (M1.6).
- **Not done in M1.3:** the pane model ("one pane now, shaped for two"): the host tracks one shown tab, and a pane abstraction arrives with split view (M4), since nothing in M1 needs it. Tab groups (the schema has them) and their sidebar UI are M1.4. The renderer-crash fallback ("visible view dies on its own") is M1.6 (own error pages); today only a page closing itself and app-ordered destroys are handled.

## 2026-11-13: Workspaces and storage over IPC (M1.2)
- **Dependencies:** `serde` (derive) and `serde_json`, in `core` only, for the IPC messages. Why: the shell and the app now exchange structured messages (workspace list, create, rename, colour, delete, activate); hand-written JSON parsing at a trust boundary is more code to get wrong than the standard crates. Both were already compiled in the build tree (as build dependencies of `cef`). Approved by Roy, 2026-11-13. **Rejected:** a hand-rolled parser, and a tab-separated wire format (fragile for arbitrary names).
- **Decision:** `core::backend::Backend` owns the data folder and the global database and decides every message; the host only executes what it returns. Replies are always the **full** `workspaces` state (list plus active id), so the shell never patches its own copy. Effects are `Activate(id)` and `Delete(id)`. Protocol violations (unknown name, bad or oversized JSON, unknown fields) are refused and logged, never answered; user errors (bad name, deleting the only workspace) get an `error` reply. A refusal never echoes the payload (serde's own messages quote offending values, so only the error class and position are logged). Ids from the shell go through `Id::parse` and must name an existing workspace. There is always at least one workspace and exactly one is active; the active id is saved in the global `settings` table and restored.
- **Data removal:** deleting a workspace removes the record at once, closes its views, and removes its folders (retrying for a while). **Correction (M1.3):** M1.2 first concluded that Chromium holds a deleted profile open until the process exits. That was wrong: it was the browsers never closing (see the M1.3 entry, wrapper panels), so their profile stayed in use. With that fixed the data is removed while the app runs. The sweeps stay as a safety net: `Backend::open` sweeps before CEF starts, and the host sweeps again right after CEF shuts down (retrying a few seconds for child processes), so anything a crash or a locked file left behind is gone at the next exit or start. The sweep only ever removes folders named like a workspace id (kind `ws`); CEF's own folders in `chromium-root` are never touched.
- **Isolation:** one request context per workspace, created on first show, with its cache folder a direct child of `chromium-root` (checked). `tools\m12-workspaces.ps1` shows two workspaces on the same site have separate cookies and localStorage, and that each keeps its own after a restart.
- **Runs on the UI thread:** the backend's SQLite calls run on the CEF UI thread, not on a storage thread as `planning/m1-plan.md` section 4 describes. Why: each message is one tiny local write today. The call site is a single place (`host/src/ipc.rs`), so moving it behind a channel later changes nothing else. Revisit when tabs and history add volume (M1.3 and later).
- **Not done in M1.2:** the colour frame around the page and workspace colour in the title (M1.4). Tab restore and keyboard shortcuts for workspace switching arrived in M1.3.

## 2026-11-13: How the shell is served and how IPC v0 is guarded (M1.1)
- **Decision:** The shell is served from the custom scheme `app://shell/`, registered `STANDARD | SECURE | CORS_ENABLED | FETCH_ENABLED | DISPLAY_ISOLATED`, from a `ui` folder next to the executable (a copy of `ui/dist` made by `tools/build.ps1`). The shell view uses CEF's global request context, never a workspace context, so it shares no cookies or storage with a page. `window.m0` is installed in the renderer only for a main frame whose URL starts with `app://shell/`. The browser process checks again on every message: the sending view must be the shell view and its frame must still be an `app://shell/` page; anything else is dropped and logged. What a message means is decided in `dev_browser_core::ipc` (v0: `ping` answers `pong`, unknown names and payloads over 64 KiB are refused). Replies reach the page as a call to `m0.onmessage(name, payload)` with both strings escaped as JavaScript literals.
- **Why:** two independent checks (renderer binding, browser gate) mean a page that somehow gets the binding, or a compromised renderer that skips JavaScript, still cannot talk to the app. `DISPLAY_ISOLATED` stops other origins embedding or linking to the shell. Serving from a folder keeps the first slice small; the path resolver (`shell::resolve`) refuses `..`, backslashes, colons and drive letters and is unit-tested.
- **Rejected:** embedding `ui/dist` in the binary now (needs a dependency or a build script; the folder can be replaced by embedding later without touching callers); a V8 accessor for `onmessage` (calling a plain property through `execute_java_script` is simpler and the payload is escaped); trusting the frame URL seen by the renderer alone.
- **Checked (2026-11-13), `tools/s6-hostile-page.ps1`:** a hostile http page sees no `window.m0` (own or `top`), and its fetch, XHR and iframe to `app://shell` all fail. **Finding:** a page view cannot load `app://shell` at all (`ERR_UNKNOWN_URL_SCHEME`), because the scheme handler is registered only on the global request context and workspace contexts do not inherit it. That is a stronger first line than planned, but it depends on the factory staying global-only, so the script checks it (part B). The browser-side gate (`ipc::trusted`) is unit-tested but not exercised end to end, since no page can reach it; a compromised-renderer test would need a test hook and is left for M1.7. The script was also shown to fail when the renderer installs `window.m0` for every page.

## 2026-11-12: Dependencies for the M1 foundation
- **Decision:** Rust `core`: `rusqlite` with the bundled SQLite (the same crate and feature `home_screen` uses; the spec's storage is SQLite). UI: `preact` and `@preact/signals` (the `home_screen` stack, so its components drop in at M2), `vite` and `@preact/preset-vite` (build), `vitest` and `jsdom` (tests). Nothing else yet; `cef` and `cef-dll-sys` arrive with the `host` crate (see the shell decision).
- **Why:** each has one job and no cheaper standard-library or platform route: the standard library has no SQLite, and a sidebar with groups needs a view layer and a build step.
- **Rejected:** a CSS framework in the shell for now (`home_screen` uses Tailwind and daisyUI; revisit when the sidebar needs it); an ORM or migration crate (a small hand-written migration runner is enough and easier to test).
- **Cost in bytes/deps:** the UI bundle is small (Preact is about 4 KB gzipped); SQLite adds roughly 1 MB to the binary. Space is not a constraint here (Roy, 2026-11-12), so these are recorded for review, not as a budget.

## 2026-11-12: Data location, `%LOCALAPPDATA%\dev_browser\` (D6)
- **Decision:** All application data lives under `%LOCALAPPDATA%\dev_browser\`: global `browser.db`, `chromium-root\` (CEF's root cache path, one direct child per workspace), and `workspaces\<id>\` with each workspace's `browser.db` and `homescreen.db`. Workspace folders use generated IDs, never names. A `--data-dir` flag overrides it for tests.
- **Why:** it matches the spec's layout and keeps browser data out of roaming profiles. The override keeps tests and the spike-style tools away from real data.
- **Rejected:** `%APPDATA%` (roams, and would sync browser data between machines); a folder next to the executable (breaks on read-only installs).
- **Cost in bytes/deps:** none.

## 2026-11-12: What CI covers (D5)
- **Decision:** CI builds the Rust crates that do not need CEF, runs `cargo test` and `cargo clippy`, runs the UI unit tests and the docs build. The GUI checks (real input, window capture, frame analysis) stay local scripts in `tools/`. Adding the CI workflow itself needs Roy's approval first (it is deploy-adjacent configuration).
- **Why:** a hosted Windows runner has no interactive desktop, and the M0 checks need one. They found defects logs and unit tests missed, so they stay part of "done", run by hand before a slice is called finished.
- **Rejected:** running the GUI checks in CI (unreliable without a desktop); skipping them (they paid for themselves in M0).
- **Cost in bytes/deps:** none.

## 2026-11-12: cef-rs and CEF version policy (D4)
- **Decision:** Pin cef-rs to an exact git revision and CEF to the version it targets. Upgrade deliberately, on a schedule that follows Chromium security releases, and re-run the `tools/` checks (and the M0 wrapper and destroy scenarios) on every upgrade. Record each bump here.
- **Why:** crates.io 156.4.0 did not build (the CEF download step fails on the CDN index size), so a git pin is needed anyway; a pin also makes builds reproducible and makes picking up a Chromium security fix a conscious step rather than an accident. The spec makes a security-update strategy mandatory before important accounts are used.
- **Rejected:** floating on crates.io or `main` (builds change under us); vendoring cef-rs (more to maintain).
- **Cost in bytes/deps:** one pinned git dependency; a CEF export step per machine (`tools/`).

## 2026-11-12: First supported OS is Windows (D3, confirmed by Roy)
- **Decision:** Windows is the first supported platform. Platform-specific code stays inside the `host` crate. Linux and macOS are separate, later commitments, each with its own test and packaging work.
- **Why:** it is the only platform the M0 spike validated and the one in daily use.
- **Rejected:** building for several platforms from the start (each multiplies the test and packaging work before there is a working product).
- **Cost in bytes/deps:** none.

## 2026-11-12: How the shell talks to Rust (D2)
- **Decision:** The shell view and the Rust host talk over CEF process messages with a small V8 binding (`window.m0`) that the render process installs **only** for documents served from the private `app://shell` origin. Web pages get no binding. Commands and events are typed: one Rust enum, one TypeScript type generated from it. The Rust side resolves the caller from the frame that sent the message, never from a field in the message.
- **Why:** it replaces the spike's page-title hack, keeps privileged IPC out of web pages by construction (the first S6 check), and makes caller identity something the browser knows rather than something a page claims.
- **Rejected:** a localhost HTTP server (reachable from any page and any local process: fine for a personal start page like `home_screen`, not for a browser); `cefQuery` (works, but is a generic string channel we would have to type ourselves).
- **Cost in bytes/deps:** none beyond the cef crate.

## 2026-11-12: Shell UI is Preact in trusted browser views (D1, confirmed by Roy)
- **Decision:** The sidebar, toolbar and later the launcher and widget panel are Preact (with signals) apps built with Vite and loaded in trusted browser views from `app://shell`. They are not CEF Views widgets.
- **Why:** the launcher and tools in M2 and M3 are `home_screen` code, which is Preact; one stack means they drop in. The spike's overlay and divider already prove trusted views work in a Views window. Views widgets cannot do a sidebar with groups and drag in a reasonable amount of code.
- **Rejected:** CEF Views widgets for the chrome (too limited); a different framework (loses the `home_screen` reuse).
- **Cost in bytes/deps:** see the dependencies entry above.

## 2026-11-12: Shell integration: direct CEF through cef-rs (decided after the M0 spike)
- **Decision:** The browser shell is a Rust host that embeds CEF directly through the `cef` bindings from [tauri-apps/cef-rs](https://github.com/tauri-apps/cef-rs), using CEF's Views framework with Alloy-style browser views (see the entry below). Tauri with CEF is not used.
- **Why:** The M0 spike (`spike/`, results in `planning/m0-feasibility-spike.md`) ran all five tests on Windows with this stack: embedding, a browser-owned draggable overlay, `Ctrl+P` interception from a page, an input and an iframe, one request context and profile per workspace that survives restarts without leaking, and two panes with a saved divider, outlines and flash-free workspace swaps. It also showed the pieces M1 to M3 need work: per-view destroy and recreate, app-owned dialogs and permission prompts, a per-workspace camera and microphone decision store, and a render-process wrapper that stops live capture. Direct CEF gives the control this needs (request contexts, pre-key-event handler, frame and render-process handlers).
- **Rejected:** Tauri with CEF: never tried. It would give a faster shell but the spec flags overlay and split-view as unproven there, and the spike made direct CEF work, so there was no reason to take on a second integration layer. Revisit only if direct CEF is dropped for another reason (maintenance, packaging, a platform it cannot reach).
- **Cost in bytes/deps:** CEF runtime about 426 MB extracted for the minimal Windows x64 build (installed size of our own binary plus runtime still to be measured and published). Dependencies: `cef` and `cef-dll-sys` (cef-rs, pinned to a git revision because crates.io 156.4.0 could not build: its CEF download step fails on the CDN index size), CMake and Ninja as build tools on Windows, and a one-time CEF export (`export-cef-dir`) with a local patch to the download limit. None of this ships in our own code.
- **Known caveats carried forward:** validated on Windows only (Linux and macOS untested); the GPU process crashed at start-up with several views until DirectComposition was disabled (root cause and cost unknown); IME and real OS-level DPI scaling were not checked; a page can defeat the capture-stop wrapper, so a browser-side reload fallback is required; Alloy-style views mean downloads, permission prompts, dialogs and error pages are ours to build.

## 2026-11-12: Alloy-style browser views inside the Chrome bootstrap (confirmed by M0)
- **Decision:** Build panes and the overlay as Alloy-style CEF BrowserViews. Confirmed in the M0 spike: tests 2, 3 and 5 were run with real input and screenshots and pass.
- **Why:** Chrome style hosts one browser per window; split view and a browser-owned overlay need several. CEF kept Alloy style on purpose for this (cef issue 3681) after removing the Alloy bootstrap in M128.
- **Rejected:** Chrome style for everything (one browser per window); one native window per pane (not tried, awkward for a single-window design).
- **Cost in bytes/deps:** None. Chrome features (downloads UI, permission prompts, error pages) become ours to implement. Keep the style choice in one place.

## 2026-11-12: Chromium is a deliberate exception to the Floppy Rule
- **Decision:** Accept CEF/Chromium as the rendering runtime. Hold everything we write (Rust code, shell UI, docs) to the Floppy Rule, and measure and publish the installed size of the runtime honestly.
- **Why:** Writing a rendering engine is out of scope, and web compatibility is the point of a daily-driver browser.
- **Rejected:** A platform webview (weaker per-workspace session isolation); a new engine (non-goal).
- **Cost in bytes/deps:** Large (the CEF runtime). Exact figure recorded after M0.

## 2026-11-12: Shell integration is undecided (superseded by the decision above)
- **Decision:** Do not choose before the M0 spike. Both candidates are evaluated against the same five tests (`planning/m0-feasibility-spike.md`).
- **Why:** Binding maturity, overlay layering and multi-view behaviour are unproven; the spec marks this "to validate".
- **Rejected:** Picking a framework first and building around it.
- **Cost in bytes/deps:** None yet.

## 2026-11-12: Two SQLite databases per workspace, plus one global
- **Decision:** Global `browser.db` holds only workspace metadata and preferences. Each workspace has `browser.db` (history, bookmarks, tabs, groups, search) and `homescreen.db` (launcher, widgets, tool instances). Chromium keeps cookies and site storage in its own per-workspace context.
- **Why:** Isolation and independent migrations. This is data organisation, not a security sandbox; cross-database atomic transactions are not assumed.
- **Rejected:** One shared database with a workspace column (easy to leak across workspaces); copying bookmarks into Home Screen storage (duplication).
- **Cost in bytes/deps:** SQLite, already used by `home_screen`.

## 2026-11-12: Rust core with Chromium rendering; reuse Home Screen UI and tools
- **Decision:** Rust application core, embedded Chromium, launcher and bundled tools taken from `home_screen` behind a typed IPC and a capability broker.
- **Why:** Agreed in spec v0.1 (see the decision log in `planning/home-screen-browser-spec.md`).
- **Rejected:** Chrome extension (cannot own the launcher or isolate sessions this way); Electron-style shells as the default.
- **Cost in bytes/deps:** To be measured.
